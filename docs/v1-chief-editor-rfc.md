# 主编：以对话为核心入口的创作架构（RFC）

> 状态：已通过；第 1 期已实现，D74 与各节修订已写入《[v1 架构基线](v1-architecture-plan.md)》，与本文的出入以 D74 为准（2026-10-12）。产品细节随各期写入工作台产品文档；全部吸收后删除本文（§13）。

## 1. 为什么要改

现在的输入框不是对话。回车后的文字由界面按“当前选中位置”定作用域，落成一条要求（`composerScope`）；有稿件等你决定时，同一段文字又被当成修改意见。它本质上是一个没有模型的分诊器：

- 实例：运行中输入“第二章的标题换一个长一点的”，当时选中的是第 21 章，于是落成了“第 21 章的要求”。第 21 章被判过期重写，标题改成了《何氏的那一炷香》；第 2 章没动，用户等了很久也没看到回应。
- 根因不在作用域算错，而在这里本该有一个能听懂话、看得到全书、能动手也能回话的代理，我们却用确定性路由顶替了它。§0.1 第二问反对“一次分诊猜动作”，我们在界面层自己又造了一个，而且连模型都没有。

系统里有规划、写手、审阅三个 Agent，却没有一个代表用户。用户控制这本书只能靠表单式输入和命令；读懂全书、分析、比较、出主意、按需修改这些 Agent 能力，对用户都是关着的。

## 2. 结论：一个面孔、一块黑板、两条回路

```text
                 用户
                  │ 对话（唯一入口）
                  ▼
                主编 ─────────────── 驾驶回路：听懂 → 改黑板 → 回话
                  │ 要求 / 提案 / 运行控制（一等对象，带来源）
                  ▼
   ┌── 黑板：作品（Project Authority）+ 连续创作（CreationRun）──┐
   └──────────────────────────────────────────────▲──────────────┘
                  │ 缺口对账（确定性）               │ 提案 / 裁定
                  ▼                                  │
             Coordinator ──▶ 规划 / 写手 / 审阅 Worker ── 生产回路
```

- **一个面孔**：主编是用户唯一的对话对象，每本书常驻一位，对话记忆持久保存。
- **一块黑板**：所有 Agent 只通过作品与连续创作协作，互不传话；主编也不给 Worker 发消息。
- **两条回路**：生产回路不变，Coordinator 按缺口对账确定性派活，Worker 产出提案与裁定。驾驶回路是新增的，用户与主编对话，主编把用户的意思落成黑板上的一等对象。驾驶回路只改黑板，生产回路只看黑板，两边不直接耦合。

一句话：**主编替用户管书，生产线替用户写书。**

## 3. 角色边界

| 角色 | 触发 | 读 | 写 | 不做 |
|---|---|---|---|---|
| 主编 | 用户的每条消息 | 全书（故事语言）、要求、审阅、运行状态、对话 | 要求、提案、运行控制 | 写正文；创建任务；批准提案；接受审阅意见 |
| 规划 / 写手 / 审阅 | Coordinator 派的任务 | 任务快照里的上下文 | 所属工作区；提交提案或裁定 | 读对话；与用户或彼此对话 |
| Coordinator | 黑板变化 | Run 与推导结果 | Run 事件、任务 | 文学判断；理解对话 |

三条硬边界：

1. **主编不写正文。** 正文只能出自写手的工作区（§6.1）。用户要改正文，主编就把它落成要求（必要时标明“现有正文不满足”，§7.4），由生产线重写。
2. **主编不派活。** 主编改的是书和目标，下一步做什么仍由缺口对账推出（§6.3）。它不创建 Operation，所以不会产生无人驱动的孤儿任务，Coordinator 推导表也不为它加分支。
3. **生产线不读对话。** 聊天里的话要影响写作，必须先落成要求、提案或运行控制。这守住了 §4.9“Directive 不是聊天记录”：Worker 的上下文只来自当前 Revision。

## 4. 主编的工具

工具集固定，按顺序编译进主编的稳定前缀（§7.4 缓存纪律）。参数用故事语言（D66），包括章号、卷弧序号、实体名、主体加谓词，由宿主解析成 ID。

### 4.1 读

| 工具 | 内容 |
|---|---|
| `book_outline` | 卷→弧→章大纲树，附每章状态（未写、已写、审阅结论） |
| `book_chapter` | 某章正文，可按段落范围读 |
| `book_facts` | 按实体或主体加谓词查当前事实及来源章 |
| `book_requirements` | 生效与已退役的要求：原话、作用域、来源、核验结果 |
| `book_reviews` | 某章或某窗口的审阅意见与用户裁决 |
| `book_history` | 最近的变更：谁、何时、改了什么，并标出哪些可撤销 |
| `book_draft` | 等用户决定的稿件：改了什么，候选章节通过后的规划、全文与设定（第 1 期实现时补上） |

运行状态不靠工具查。宿主会在每条用户消息前附一段“书况”（§6.3）。

### 4.2 写

| 工具 | 落成什么 | 署名 | 生效 |
|---|---|---|---|
| `note_requirement` | Directive：原话、作用域、可选量化约束、可选“返工” | 用户（引用） | 立即 |
| `retire_requirement` | 退役 Directive | 用户（来源消息） | 立即 |
| `reject_draft` | 否决待审稿件，理由入账为该章要求（S10） | 用户（引用） | 立即 |
| `propose_change` | 故事语言提交 → Proposal：卷弧章、实体、事实、罗盘、Intent、锁定、审批策略 | AI（主编） | 按审批策略；不能自动批准的出确认卡 |
| `revert_change` | 指定 ChangeSet 的反向提案 | AI（主编） | 同上 |
| `set_length` | 篇幅：固定章数，或交给 AI | 运行控制 | 立即 |
| `pause_creation` / `resume_creation` | 暂停或继续连续创作 | 运行控制 | 立即 |
| `renew_repair` | 卡住的章“再改一次”，重开修订预算 | 运行控制 | 立即 |

`propose_change` 用的是 Worker 提交的同一份故事语言格式（`narrative.Submission`，不含正文），在此基础上补 Intent、锁定、审批三段，经同一个 `narrative.Resolve` 和 Change Engine 校验。主编没有另外的写路径。

### 4.3 引用即署名

主编能以用户名义写入的，只有用户的原话。`note_requirement` 的 text、`reject_draft` 的理由、Intent 的字段值，都必须是对话里某条用户消息的逐字片段，并带上那条消息的编号（`source`）。宿主确定性校验两件事：`source` 指向的是用户消息，text 是这条消息的子串。不符就以工具错误返回。除此之外，主编写入的一切都署名 AI，走审批。

这样，§4.9 第 1 条“作者只能是用户”和第 2 条“原话不翻译”就成了可机器检查的约束：主编决定作用域和归类，文字本身仍是用户的。作用域判错了怎么办，见 §6.4。

### 4.4 确认分级：复用审批，不另建权限系统

| 档位 | 内容 | 机制 |
|---|---|---|
| 直接生效 | 记要求、退要求、否决稿件、运行控制，以及 Change Engine 判定可自动批准的 AI 提案 | 时间线回执一行，可撤销 |
| 确认卡 | Change Engine 不能自动批准的 AI 提案：审批策略要求确认的、碰到锁定内容的、D25 清单内的（Intent、锁定、审批策略）、影响到已写章节需要选处置方式的（S4：重写受影响章、只改后续解释、放弃） | 卡片出现在对话里，用户按键裁决 |
| 只认按键 | 批准提案；接受审阅意见（用户裁决，D43） | 不给主编这两个工具 |

哪些改动要确认，完全由现有的 Change Engine 和审批策略决定，主编只是又一个 AI 作者。用户把审批调到 manual，主编改个标题也会出确认卡，这正是“控制强度是同一个旋钮”的意思（§0.1 第三问）。批准和接受是用户的主权动作：模型替用户点“同意”，等于没有确认，所以干脆不给工具。

## 5. 一句话怎么流转

| 用户说 | 主编做 | 结果 |
|---|---|---|
| 第二章的标题换一个长一点的 | `propose_change` 改第 2 章标题 | auto 策略下直接生效，回执“第 2 章改名为《…》” |
| 这章主角要输，别让他赢（写第 5 章时） | `note_requirement`，作用域第 5 章，引用原话 | 在途的第 5 章转 stale，带着新要求续写（§4.9 第 5 条） |
| 接下来安排反派登场 | `note_requirement`，作用域从下一章起 | 在途任务不受影响（S12） |
| 第 8 章太拖了，紧凑点重写 | `note_requirement`，作用域第 8 章，标记返工 | 推导器派重写，审阅按要求核验 |
| 结局改成悲剧 | `propose_change` 改 Intent 结局（引用） | 出确认卡；确认后相干的审阅证据按基线失效 |
| 第 10 章李四其实早就知道秘密 | `propose_change` 改事实 | 出影响报告和确认卡，三选一（S4） |
| 写到 60 章收尾 | `set_length 60` | 运行目标更新 |
| 第 3 章有什么问题？帮我想想下一卷 | 只读、分析、讨论 | 不改书；用户点头后再落成要求或提案 |
| 先停一下 | `pause_creation` | 创作暂停 |
| 刚才那条记错了，是第 2 章 | `retire_requirement` + `note_requirement` | 两行回执 |

## 6. 运行与交互

### 6.1 主编只在用户说话时说话

主编的每个回合都由一条用户消息触发。生产线的等待、失败与完成不会叫醒主编，而是以确定性卡片进入时间线（和现在一样，不花模型调用）；用户下次开口时，书况里会带上这些变化。这样成本可预期，也省掉了“只有用户回合才能写”这类门控，因为主编本来就只有用户回合。

### 6.2 两条回路并行

- 生产运行时用户照常对话，不必先暂停（S12）。主编的改动就是普通 ChangeSet，对在途任务的影响全按内核既有规则走：作用域相交就转 stale 并继承工作区，不相交就把提案重定位（§5.5 第 4 条）。不新增任何协调规则。
- 主编回合进行中用户又发了消息：作为 steering 送进当前回合（agentcore `Agent.Steer`），而不是排到下一回合。

### 6.3 书况

宿主在每条用户消息前附一段书况：确定性渲染，用故事语言，几百字以内。内容包括进度与篇幅、运行状态、当前任务、待你决定的事项（带编号，便于主编在回话里指向）、用户正在看的章，以及上一回合以来的里程碑。书况放在动态尾部，不破坏稳定前缀的缓存。

“用户正在看的章”只作为参考信息交给主编，由它和用户的原话一起判断，不再像 `composerScope` 那样直接决定作用域。第 2 章与第 21 章的误判就出在这里。

### 6.4 回执与纠错

主编每调用一次写工具，时间线里就留一行回执，例如 `✓ 记下要求 · 第 2 章 ·「标题换一个长一点的」`、`✓ 第 2 章改名《…》· 可撤销`。回执由宿主按工具结果渲染，不依赖主编复述。用户一眼就能看到作用域，错了说一句话就能纠正。这是对“作用域会判错”的根本回答：不追求猜得更准，而是让结果立刻可见、可以撤销。

### 6.5 按键

| 键 | 行为 |
|---|---|
| 回车（有字） | 发给主编 |
| 回车（空） | 有确认卡时展开卡片；创作停着时继续；否则阅读当前内容 |
| `y` | 确认当前卡片（批准提案或接受意见） |
| Esc | 主编回合进行中先中断回合，否则暂停创作；永不退出 |
| Ctrl+C 两次 | 退出 |

暂停后说话即继续：创作因 Esc 暂停时，主编回合结束后创作自动继续，除非主编在这个回合里调用了 `pause_creation`（用户说了“先别写”）。这保留了“想停按 Esc，说句话就接着写”的现有体验，判定也是确定性的。

### 6.6 时间线

工作台主栏是一条时间线：用户消息、主编回话、主编回执、生产里程碑（第 n 章完成、审阅结论、等待）按时间交织，在途任务的实时流仍在末尾。右栏的“创作团队”多一行“主编”，其余不变。

## 7. 数据与运行时

### 7.1 对话记录

- 新表 `conversation_messages(project_id, seq, epoch, payload, usage, created_at)`。`payload` 是 agentcore.Message 的 JSON，每本书一条对话。消息一结束就落盘，与 Worker 转写同一纪律：落盘失败即停止。
- 压缩用 agentcore 的 `CompactAt` 加 `compact.Summarizer`。压缩结果写成新 epoch，模型只加载最新 epoch，界面回看时读全部。
- 对话不是权威：不进 Revision、不进导出投影、不进任何 Story Context。它只是交互状态加来源记录。
- 加表意味着 schema 升到 9。按 D38，旧的开发库会被拒绝打开，现有的书需要新建（v1 未发布，不做迁移）。

### 7.2 来源与返工字段

- Directive 新增 `source`，指向对话里的用户消息，是“引用即署名”的校验对象。
- Directive 新增 `rework`：这条要求同时声明“作用域内的现有正文不满足”。
- Proposal 新增 `source`：主编提出的提案指回触发它的用户消息，作者为 `ai/chief`。

### 7.3 主编的 Prompt 与模型

- Prompt 是官方包里的新 Slot `chief.converse`，经同一个 Prompt Compiler，与 Creator Profile、Project Overlay 叠加。稳定前缀是核心协议加主编契约加工具，冻结后可缓存（§7.4）。Slot 只写方法：怎样区分要求、修改、提问和运行控制，什么时候追问，回话要简短，不写正文。
- 模型角色新增 `chief`，`/model` 可以单独绑定，比如换一个便宜快速的模型。
- 用量记在对话消息上，创作团队栏的“主编”一行按书累计。

### 7.4 返工要求进入推导链

小说推导器新增一类缺口：作用域内、正文最后一次变化早于这条返工要求入账的章，派重写任务，任务输入带上要求原话。重写后正文更新，缺口自然关闭，再由审阅核验。这就是 §6.3 已列明的“用户显式发起的任务”这一缺口来源，落在 `app/novel` 的纯规则里，Coordinator 零改动。用户发起的返工不消耗自动修订预算，因为预算只管无人过问的连续重写。

### 7.5 章节标题只存一处

现在标题同时存在计划节点和正文里，改标题会改动正文文档，触发该章事实待核验（D41），平白多一次核验任务。改为标题只存在计划节点，正文不存标题。此后改标题只是一次计划修订：所在窗口按证据基线重审一次（这个代价可以接受），不再触发事实核验。

## 8. 模块落位

```text
internal/
├── app/chief/          主编用例：Session（Send / Interrupt / Thread / Subscribe）、工具实现、书况渲染、引用校验
├── infra/capability/   + Conversation：封装 agentcore.Agent（模型绑定、缓存键、压缩、落盘、活动）
├── infra/store/        + conversation_messages
└── entry/tui/          输入框只通往主编；时间线交织；确认卡
```

- 工具在 `app/chief` 里定义，handler 只调用现有的具名用例：`project`（要求、锁定、审批、快照）、`decision`（提案、否决、回滚）、`novel`（篇幅、修订预算、暂停与继续）、`workbench`（读模型）。主编不碰 store，也不碰 change、operation 引擎。
- `infra/capability` 提供通用的 Conversation，不理解主编工具的语义；工具通过 capability 声明的小接口传入。
- entry 的写操作只剩两类：按键（批准、接受、继续、暂停）和对话。archtest 白名单登记 `app/chief`。

## 9. 删掉什么

- 输入框分诊：`composerScope`、`inputScope` / `inputLabel` / `inputDecision`、“等你决定时文字就是修改意见”的分支，以及 `n` 的提示。
- `/goal`：直接说“写到 60 章”。命令只留与书内容无关的 `/model`、`/export`、`/diag`、`/view`、`/help`，以及 `/章号` 跳转。
- 决策卡上的文字输入路径：否决理由由主编通过 `reject_draft` 引用入账。
- “要求只能加不能退”的缺口自然消失，主编可以退役要求。用户书里第 21 章那条误记的要求，新版里说一句就能撤掉。

## 10. 架构文档的修订

| 位置 | 修订 |
|---|---|
| §0.1 第二问 | 区分“隐藏分诊”和“对话代理”。判据：对话的每个效果都落成带来源的一等对象，立即有回执，可以撤销，而且生产线不读对话 |
| §2.2 第 1 条 | 不变。主编是新角色，不是“更多 Agent”：它补上的是一直缺位的用户代理职责 |
| §4.9 第 1、2 条 | 作者仍只能是用户；主编代录必须“引用即署名”；新增 `source`、`rework` |
| §5.1 | AI 作者包括主编；提案带来源 |
| §6.3 | 缺口来源新增“返工要求”；明确主编不创建 Operation |
| §11 / §12.1 | 新包 `app/chief`；Conversation 归 capability；对话表归 store |
| §15 | 新增 D74（主编） |

§0.4 第 1 条（控制扩展成本）不受影响：新增一种内容控制，仍然只是登记文档类型、装配上下文、核验，主编最多在 `propose_change` 的故事语言格式里多一段，与 Worker 的提交格式同步。

## 11. 风险与对策

| 风险 | 对策 |
|---|---|
| 主编判错作用域或意图 | 回执立即可见，一句话撤销或改正；拿不准时追问（写进 Slot 的方法） |
| AI 借主编冒用用户署名 | 引用即署名，宿主确定性校验子串与来源 |
| 主编和生产线同时改同一处 | 内核已有规则：基线版本、提案重定位、stale 后继 |
| 对话越来越长，成本上升 | 稳定前缀缓存、按阈值压缩、`chief` 角色可单独绑定便宜模型 |

## 12. 不做

- 主编主动发言（生产事件叫醒主编）。
- 首页用对话建书：新书仍走向导，进入工作台后由主编接手。
